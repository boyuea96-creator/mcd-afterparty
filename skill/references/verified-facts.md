## 二、关键字段（已验证）

### query_nearby_stores（到店）
- 入参：仅 `beType` / `city` / `keyword` / `searchType`（**无半径/数量参数**，筛选靠返回列表自行排序截断）。
- 返回：`storeName` / `address` / `distance`(米) / `businessStatus` / `businessStartTime` /
  `businessEndTime` / `reservation`(是否支持预约) / `reservationTimeOptions`（今明两天时段文本，
  如「午餐(10:44至14:15)…宵夜(22:14至22:46)」）。
- 实测教训：最近门店可能 `reservation=false`；**不能只按距离选店**。
- ⚠️ **门店经纬度字段实测全为 0** —— 做通勤必须先「地址文本 → 高德地理编码 → 坐标」。

### query_meals（菜单，到店 vs 配送编码体系不同）
- 到店：`orderType=1`，`beType=1`，按 `storeCode` + `reservationDate`(时段内任一时刻)。
- 配送：`orderType=2`，`beType=2`，按 `storeCode` + `beCode` + `reservationDate`(送达时刻，格式 `yyyy-MM-dd HH:mm`)。
- 返回：分类、餐品编码、名称、现价、原价、`discountType`。
- `discountType` 实取值含 `促销优惠` 与 `随单购麦金卡优惠`（后者带 `withOrder{membershipCode,specId}`，
  无卡按 `originalPrice` 计）。
- **菜单逐店独立**：同商品不同店价格可不同（麦香鸡实测 17 元 vs 16.5 元），不可跨店复用。

### query_meal_detail（套餐选配 / 明细）
- 返回：`rounds[]`（每轮 `name`/`quantity`/`maxQuantity`/`minQuantity` + `choices[]`），
  每个 choice 含 `code`/`name`/`quantity`/`isDefault`/`diffPrice`/`supportModify`/`modification`。
- 含 `unselectedKey` 的特调组必须把未选项键一起传，否则 `calculate_price` 报错。
- ⚠️ **套餐里到底有什么，必须用本工具真查**——用户挑套餐看的就是「哪个汉堡 + 哪份小食 + 饮料」。
- **套餐默认构成（配送实测，京港国际 3330199/333019902，2026-10-16）**：
  - **吃鸡盛宴四人餐 `9900013006`（¥107）**：麦辣鸡腿堡 ×2 + 板烧鸡腿堡 ×2 + 麦辣鸡翅 2 块 + 中薯条 + 麦乐鸡 5 块 + 可口可乐中杯 ×4；饮料可换「多汁柠柠」+¥1 /「鲜萃冰咖」+¥2 / 麦咖啡系列 +¥8~10。
  - **快乐吃鸡双人餐 `9900012938`（¥55.9）**：麦辣鸡腿堡 + 板烧鸡腿堡 + 麦乐鸡 5 块 + 可口可乐中杯 ×2；汉堡可换「巨无霸」+¥3、「双层吉士」+¥1，小食可换「麦辣鸡翅 2 块」+¥1、「玉米杯(大)」+¥2。
- **差价随套餐而异、以当次返回为准**：同一补位项在不同套餐差价不同——「玉米杯」在麦辣堡中套餐 `9900002995` 实测 **−¥1**，但在快乐吃鸡双人餐 `9900012938` 为 **+¥2**，**不可套用**。
- **「加量/管饱」不限于饮料（本次补）**：套餐的**主食轮 / 小食轮本就可替换 / 加量**——
  双人餐 `9900012938`：小食轮可换「中薯条」+¥0、「麦辣鸡翅 2 块」+¥1、「玉米杯(大)」+¥2；汉堡轮可换「巨无霸」+¥3、「双层吉士」+¥1；
  四人餐 `9900013006`：「选择小食一」可换「麦乐鸡 5 块」+¥0。提示"更管饱"时优先给**加肉 / 加小食**，而非只加可乐。
- ⇒ **默认项未必最便宜**；差价数据可直接喂省钱引擎。

### calculate_price（试价）
- 到店：storeCode + orderType=1 + beType=1 → 返回 `takeWayList`：`eat-in`(堂食) / `locker-in`(取餐柜)。
- 配送：storeCode + beCode + orderType=2 + beType=2 → 返回 `deliveryPrice` / `packingPrice` /
  `tablewarePrice`（`needTableware=false` 除非用户要餐具）。
- ⚠️ **总价取顶层 `data.price`**；`productList` 里插入的「打包服务费」行 `subtotal=0`，**对明细求和会漏算打包费**。
- 券后价：items 里附「券商品编码 + couponId + couponCode」；券商品编码不在常规菜单中，必须来自券查询；
  不带券试券商品返回 0/空列表；服务端按「张」归一数量。

### 优惠券（三个来源，2026-10-16 实测厘清）

**① `available_coupons`（无参数）= 麦麦省券池，含「还没领」的券** —— **唯一能看到「可领取」券的入口**
- 返回每条含：`优惠券标题` / `状态` / `优惠券图片`；`状态` 实测两个取值：**`已领取`**、**`可领取`**。
- 实测（2026-10-16，杭州账号）：4 条 `已领取`（中薯条买一送一、王牌小食拼、巧克力味厚松饼猪柳蛋套餐 ×2）
  + **3 条 `可领取`（免费脆薯饼、人气麦旋风买一送一、9.9元中杯冰美式）**。
- ⚠️ **`可领取` 的券不在卡包、不在门店券池、没有 `couponCode`** → 跳过这一步就整个漏掉，
  省钱引擎算出来的价与实际能享受到的价对不上。
- 领券 = 写入动作（`auto_bind_coupons` 亦属写入）→ 本技能**只提示入口、不代领**：
  **麦当劳 App / 微信小程序 →「麦麦省」→ 找到该券 → 领取**。

**② `query_my_coupons`（可分页，`page`/`pageSize`）= 卡包「已领」券**
- 字段：`couponId` / `couponCode` / 用券价 / 有效期 / 限定星期与时/到店外送标签 / `enable`。
- 实测 **7 张**；其中「中薯条买一送一」「王牌小食拼」标签为 **`今日到期`**，
  有效期 `2026-10-12 10:30 ~ 2026-10-16 23:59`、星期限 **周一~五**、时段 `10:30-23:59`
  → **2026-10-17（周六）散场时全部失效**（撞周六限制）。
- **跨零点 / 周末散场很多券因时段或星期限制不可用，须逐条校验，不可只看有效期。**

**③ `query_store_coupons` = 已领 ∩ 该店该时段可用（唯一能试价的券源）**
- 字段：`couponId` / `couponCode` / `tradeDateTime` / `products[].productCode` / `promotionId`；
  **外送（beType=2）必传 beCode**，缺报 `600048`。
- 实测（杭州 ONE聚场 `3330547`，到店，`2026-10-16 20:40`）：**卡包 7 张 → 只返回 2 张**
  （中薯条买一送一 `9900012387`、王牌小食拼 `9900016371`），早餐券因时段不符被过滤。
- 券商品编码（`9900012387`、`9900016371`）**不在常规菜单编码中**，必须来自券查询。

**券三态对照（务必分清）**

| 态 | 取数工具 | 有 `couponCode`？ | 能否 `calculate_price` |
|---|---|---|---|
| ① 池里可领（未领） | `available_coupons`，`状态=可领取` | ❌ | ❌ 只能给「去领 + 理论可省」 |
| ② 已领在卡包 | `query_my_coupons` | ❌（仅 `couponId`） | ❌ 还需过门店校验 |
| ③ 已领 ∩ 该店该时段可用 | `query_store_coupons` | ✅ | ✅ |

### 麦乐送链路
- `delivery_query_addresses`：返回账号保存地址列表与 `addressId`；空列表=无保存地址（异常分支 A）。
  ⚠️ 返回模板**强制展示**联系人/电话/地址（PII），仅允许出现在对用户本人的对话回复中，不落盘。
  **（v0.9）这一层就是「落脚点地址」的来源**：第一屏读取它**预填**，用户可改；
  **工具只读、不能建地址**（`delivery_create_address` 禁用）——账号里没有当地地址时，
  如实告诉用户「先去 App 里加一个」，**不要拿外地门店硬算**。
- `delivery_query_stores`（beType=2，addressId）：可配送门店含 `storeCode` + `beCode` 与未来 3 天配送时段。
- 配送菜单独立编码：巨无霸 `901100` vs 到店 `1100`；薯条 `501205` vs `4810`；带「外送价格」标签且价格不同。
- 多人分享餐：双人 55.9 / 三人 86 / 四人 107 元起（可按人数直接映射）。

- 连通性与鉴权检查：`code=200` 正常；非 200 → 异常分支 E，停止流程。

## 三、异常错误形态（已验证）

- `600057`：打烊/非营业时段请求菜单「门店可能已关闭或不在营业时间」→ 异常分支 C。
- `600052`：`reservationDate` 格式错「格式为 yyyy-MM-dd HH:mm」→ 异常分支 F。
- `600048`：外送（beType=2/5/6）缺 `beCode`「外送场景下必传 beCode」→ 异常分支 F。
- `600053`：预约时刻非未来「预约时间必须为未来时间」→ 异常分支 G。
- 跨零点：24h 门店（营业 `00:00–23:59`）凌晨时段挂在**次日日期**名下，`reservationDate` 用到达时刻日历日期；
  打烊门店午夜后返回 `600057`。

⇒ **最贵/最省差 ¥39（¥13/人），是同场交通费差（全步行 ¥0 ↔ 全打车 ¥16，差 ¥8）的 4.9 倍。**
⇒ **「选错买法」比「选错交通方式」更贵——这是本技能把篇幅押在第二部分的实证依据。**

- **⚠️ `calculate_price` 支持 `roundList` 指定套餐选配（此前未记录，必须用）**：
  ```json
  { "productCode": "9900013304", "quantity": 3,
    "roundList": [
      { "round": "1", "comboItemList": [ { "code": "521316", "quantity": 1 } ] },
      { "round": "2", "comboItemList": [ { "code": "3505",   "quantity": 1 } ] }
    ] }
  ```
  `round` 取 `query_meal_detail` 返回的 `rounds[].id`（字符串），`code` 取该轮的 `choices[].code`。
  **不传 `roundList` 时按 `isDefault=1` 的默认选中项算价**——这也是为什么"默认 ¥44.70、
  选 −¥1 主食后 ¥41.70"必须分别试价，不能靠加总猜。
- **⇒ 实用结论：同一份随心配，蓝区换「高达吉士双牛堡」(−¥1) ＋ 粉区换「锡兰红茶」(＋¥0)，
  3 份从 ¥44.70 降到 ¥41.70**，且汉堡**更好**（双牛 vs 双层吉士）。**这是"选对不选贵"的最佳示例。**

- **「1+1 随心配」的两轮结构**（`9900013304` 人气经典随心配 ¥14.9，两轮均必选 1 件）：
  - **蓝区（主食）**：双层吉士汉堡 +¥0（默认）／**高达吉士双牛堡 −¥1**／麦香鱼 +¥0／
    那么大鸡排 −¥1／酥酥多笋卷 −¥1／麦乐鸡 5 块 −¥1／麦香鸡 −¥1／小薯条 −¥1；
  - **粉区（饮品/小食）**：可乐麦炫酷 +¥0（默认）／可乐中杯 +¥0／阳光柠檬红茶 +¥0／
    **锡兰红茶 +¥0（热饮）**／玉米杯／香芋派／迷你新地／迷你朱古力新地／鲜萃冰咖／雪碧／无糖可乐…；
  - ⇒ **「不吃冰」的解法 = 粉区选「锡兰红茶」，＋¥0，不必换套餐**——这比"可选热饮 +¥1"的老说法更准。
  - ⇒ 蓝区选 −¥1 的品还能把单价压到 **¥13.9**（3 份 ¥41.70）。

- **⚠️ 外送菜单可能没有「1+1 随心配」入口（关键，决定外卖贵不贵）**：
  实测万达店外送分类为人气热卖／多人分享餐／麦麦周末／麦金卡专享／大堡口福／鸡肉汉堡卷／
  巨无霸牛鱼肉堡／蘸酱炸鸡／安格斯MAX／炸鸡／开心乐园／小食甜品／500大卡／饮品 —— **无随心配**。
  外送最低**单人套餐**为「辣」么快乐套餐 `9900011124` **¥28.5**（堂食同款随心配仅 ¥14.9）。

## 消费者着重点判定 · 标定样本（v0.6.1 新增）

> 用途：给 `SKILL.md` **Step 0.6** 提供一组"该怎么判、该怎么写"的参照。**判定与推导都不进输出界面。**

**样本：泰州场（2026-10-17 周六 15:30 散场 / 3 人 / 人均 ¥40 / 不能吃冰 / 去向汉庭优佳·万达店）**

**四维判定：**

| 维度 | 本场信号 | 权重 |
|---|---|---|
| **特定需求（温度）** | 用户明确说「不能吃冰」 | **主（硬约束，一票否决）** |
| 价格 | 人均 ¥40 预算、3 人 AA | 次 |
| 疲劳 | 15:30 白天散场，未提累 | 低 |
| 时间 | 周六下午，无末班车压力 | 低 |

**否定 → 肯定翻译**：`不能吃冰` → **「想喝口热的」** ← 这才是钩子。
（反面写法：「已排除冰品」＝复述用户的限制，读起来是"你被限制了"，不是"你被满足了"。）

**硬约束必须两条路径都兑现（本场实测的落地方式）：**

| 形式 | 怎么满足「要热的」 | 代价 |
|---|---|---|
| 堂食 | 随心配**粉区选「锡兰红茶」＝热饮** | **＋¥0**（在 ¥41.70 里，已试价） |
| 外卖 | 外送菜单里**只有三人餐能换热饮**；最省的双人餐＋补堡（¥90.90）只有可乐，只能选「去冰」 | 畅享吃鸡三人餐 ¥94.80 ＋ 换锡兰红茶 **¥1/杯 ×3**（`query_meal_detail` 的 `diffPrice`，**未整体试价**） |

⇒ 一句话写成「想坐着吃口**热的**、还有力气走 → 堂食（粉区免费换热红茶）／
累到不想动 → 外卖（只有三人餐能换热饮）」——**两边都交代**，用户选任一路都不会落空。

**反例校验（Step 0.6 自检第 2 问）**：
旧句「想坐着吃口热的、还有力气走 → 堂食；累到不想动、想回酒店就吃上 → 外卖」
把「热的」只挂在堂食一侧，外卖一侧没交代 → **选了外卖的人才发现没热饮**，等于硬约束没兑现。
判定对了、句子没写全，同样是不合格。

## 外卖 vs 堂食 · 到手品质差（v0.6.2 新增，用户指出）

> 性质：**用户经验指出 + 常识事实**，不是接口返回值（API 不会告诉你"送到时还烫不烫"）。
> 但它必须影响输出措辞——**因为它是"能选"和"能吃到"之间的差距**。

**核心结论：温度和口感是外卖结构性拿不到的，不是选品问题。**

| 品质 | 堂食 | 外卖（出餐到入口约半小时） |
|---|---|---|
| 热饮 / 热食温度 | 现做现喝，**到嘴还是烫的** | **热的凉成温的**，纸杯 + 封盖 + 一路吹风 |
| 冰饮 | 冰还是冰 | **冰化成常温**，冰块融了就是一杯糖水 |
| 薯条 | 刚出油锅，脆 | **闷在纸盒里回软** |
| 汉堡 | 现拼 | 生菜出水、面包吸潮 |

⇒ **「有热饮选项」只是标称满足**。外卖保温的真实含义是「尽量不冷」，**不是「保持热」**。
⇒ 输出措辞必须分开：堂食「到嘴还是烫的」（**真兑现**）／外卖「半小时到手也就温了」（**打问号**）。
⇒ **禁止**把两边的「热」写成同一句话（如「两边都能喝到热的」）——那是把标称当实效。

**推广到所有"被时间改变的品质"**：温度、脆度、出水、气泡、冰淇淋形状。
外卖遇到这类约束，**一律标打问号**，且**不得**因此替用户否决外卖（他不在乎温度的话，外卖依然对）。

### 温度口径必须按商品分（v0.9.5 · 2026-10-20 用户抓到）

> **用户原话**：「我点的麦旋风，你还给我到手就是热的，这不搞笑吗？而且外卖和堂食你都是这么写太假了。」
> 这是把「现做」当成一个万能褒义词的后果 —— **冰品没有温度可保，只有化不化**。

| 这一单的主体 | 堂食 | 外卖 |
|---|---|---|
| 热食（堡 / 鸡翅 / 薯条 / 派 / 咖啡 / 粥） | 现做 · 到嘴还是烫的 | 现做 · 脆的送到会软 |
| 冰品（麦旋风 / 新地 / 圆筒 / 冰淇淋 / 冰饮） | 现做 · 到手还没化 | 现做 · 冰的送到会化 |
| 一冷一热（堡＋麦旋风） | 现做 · 一冷一热 | 现做 · 冰的会化 |
| 只有常温饮料（可乐 / 雪碧） | 现做 | 现做 |

**判定陷阱**：不能只靠关键词表。**「巨无霸」名字里没有「堡」字**，会被漏判成常温。
兜底规则：**能吃的、又不是饮料 → 当热食**；可乐雪碧这类**不参与**温度判断（加不加冰看用户）。

**为什么这条值得单独立规矩**：标签说错一次，用户会顺势怀疑价格也是瞎算的。
**一个假的优点，能毁掉整份方案的可信度。**

### 1. 卡是什么 —— **有两种规格，别混**

  **这是唯一硬证据**，不要据 App 的 ¥19 去反推、也不要拿 ¥19 去替 ¥9.9。
- ⚠️ **用户会拿 App 里的 ¥19 来对账**。输出必须写清渠道：
  `体验卡 ¥9.90／15 天（点餐页加购）` 或 `月卡 ¥19／30 天（App 会员页）`。
  **只写「卡费 ¥9.9」会被当成报价错了。**

| 项 | 实测值 |
|---|---|
| 卡 SKU | `521234` 麦金卡体验卡（**15 天**，不是年费） |
| 卡费 | **¥9.90** |
| 传参 | `withOrder: {membershipCode:"106", membershipSpecId:"880"}`（**不需要** cardId / cardType） |
| 生效范围 | **只对**菜单里 `discountType="随单购麦金卡优惠" && canWithOrder=true` 的商品 |

### 2. 两组对照试价（同一门店、同为到店）

| 场景 | 不买卡 | 买卡（账单含 ¥9.90 卡费） | 净变化 |
|---|---|---|---|
| **人气超值四件套随心选** `9900004236`（菜单标 ¥28／划线 ¥58） | **¥58.00** | **¥37.90**（商品 ¥28 + 卡 ¥9.90） | **省 ¥20.10** |
| **人气经典随心配 ×3** `9900013304`（¥14.9/份） | **¥44.70** | **¥54.60**（商品无折扣 + 卡 ¥9.90） | **反而亏 ¥9.90** |

⇒ **关键结论：卡值不值，只看"这一单里有没有麦金卡专享商品"。**
- 有 → 折扣常常一次就盖过卡费（四件套省 ¥30，扣掉 ¥9.9 还净省 ¥20.1）；
- 没有（如 1+1 随心配这种低价爆款）→ **买卡纯亏 ¥9.90**，必须明确劝退。

### 3. 正确算法（写进输出就这一行）

```
净省 = 该单商品折扣 − 卡费 ¥9.90（体验卡）
```

⚠️ **绝对不要**用菜单上的 `originalPrice − currentPrice` 当省额：
划线价是营销价，会把"省 ¥30"吹成账面数字，实际算上卡费只有 ¥20.10。
**必须两种都试价**：不传 `withOrder` 一次、传 `withOrder` 一次，取两个 `data.price` 之差。

### 4. 输出口径

- 有专享品：`💳 麦金卡：这单净省 ¥20.10（体验卡 ¥9.90／15 天）→ 办一次就回本`
- 无专享品：`💳 麦金卡：这单用不上（随心配不参加会员价），别买，白亏 ¥9.90`
- **不说"强烈推荐"**，只说净省与回本。

|---|---|---|

| 新地 | `9900008745` | ¥13.00（第二份半价） |

⇒ **这才是"关系改变购买清单"的硬抓手**：两个人可以吃第二份半价，一个人不会买两份。
**用它替代"女生爱吃甜"那种刻板判断**——理由是**份量＋优惠机制**，不是性别。
- 恋人 / 家人 → 「麦旋风第二份半价，两份 ¥22.5」
- 同事 / 同学 → 不提（各点各的，不会为了半价多吃一份）
- 未填关系 → **完全不提**

## 偏好解析 · 两个必踩的坑（v0.9.5 · 2026-10-20 用户实测暴露）

> **用户原话**：「我现在写了一个巨无霸的偏好你还是存在着问题，没有给我推荐对应的汉堡，
> 也没有说当下没有这个汉堡可以吃。」

### 坑 1：裸字否定词会把商品名吃掉

旧实现的否定词表是 `("不吃","不喝","不想","不要","不能","别","忌","过敏","无","少")` ——
**裸的「无」命中「巨无霸」的中间那个字**，于是「想吃巨无霸」被解析成 `avoid:["巨无霸"]`。

后果比"不推荐"更糟：不但不推荐，还**当成忌口绕开**；同时一句话还在说「要的就是这口巨无霸」。
**用户看到的是一份自相矛盾的方案。**

| 输入 | 旧结果（错） | 现结果 |
|---|---|---|
| 想吃巨无霸 | `avoid:["巨无霸"]` | `want:["巨无霸"]` |
| 特别想吃板烧鸡腿堡 | `want:["特别板烧鸡腿堡"]`（噪声没剥净） | `want:["板烧鸡腿堡"]` |
| 无糖可乐 | `avoid:["可乐"]`（把点单规格当忌口） | `want:["可乐"]` |
| 不想吃冰的冷的 | `avoid:["冰","冷","冰冷"]`（冗余） | `avoid:["冰","冷"]` |

**修法**：否定词只认固定搭配 `不(?:吃|喝|想|要|能|用|放|加|来|配)`、
`别(?:放|加|给|要|太|整)`、`无(?:糖|冰|辣|奶|芝|肉|油|盐|咖啡)`；
`无糖/去冰/常温` 这类**点单规格先摘掉再判否定**；动词前缀（吃/喝/要/来/点）单独剥。

### 坑 2：命中之后先给套餐 = 替用户花钱

旧 `pref_candidates` 先收 `kind in (combo, qxp, family)`，单品被跳过。
结果「想吃巨无霸」端上来的是**巨无霸四件套 ×3 = ¥177（人均 ¥59）**，
而真正的「巨无霸 ×3」只要 ¥79.50。

⇒ **顺序必须是：单品（最像他原话）→ 含它的套餐（配齐）。**
⇒ 「配齐」那套试价后**超过单品 1.8 倍就不摆** —— 菜单标价和试价能差出 2 倍多
（巨无霸四件套标 ¥32，试出来人均 ¥59），超了就说明它已经是另一个单，不是"稍微加点"。

**实测（武汉华罗利 `1960042` · 堂食 12:10 · 3 人）**

| 偏好 | 第 1 套 | 第 2 套 |
|---|---|---|
| 想吃巨无霸 | 巨无霸 ×3 **¥79.50** | （四件套 ¥177 已剔除） |
| 想吃麦旋风 | 经典麦旋风 ×3 **¥42.00** | ＋玫瑰红糖糍粑派 ×3 ¥57.00 |
| 想吃麦辣鸡翅 | 麦辣鸡翅 ×3 **¥43.50** | ＋派 ×3 ¥58.50 |
| 想吃火锅（店里没有） | 精选超值随心配 ×3 ¥41.70「兜底 · 没你要的那口」 | — |

**早市 8:30 想吃巨无霸** → 「这会儿没有巨无霸，**换个时段才有**」——
用明天中午的菜单探过才敢说这句（见 `pref_later`）。探不出来就**不编原因**，只说没有。
